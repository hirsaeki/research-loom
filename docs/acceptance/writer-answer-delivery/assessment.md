# #627 初回稿の比較結果

## 結論と採否

二ケース×二条件の初回稿を保存し、公開round-tripへ取り込んだ。
両条件とも、具体的な変更を勧める答えと、反対結果によって一律展開を保留する答えを保持した。
今回の限定試験では、基準側の結論が消え現行側だけで回復するという差は確認できなかった。
追加のWriter指示やProfile条項は採用しない。

#626の変更は、保存済みの正の通信事項を欠落させないための配信修正として維持する。
それを文章改善の因果効果の実証と扱わない。
ChatGPT Workでの執筆・統合受入と実読者の理解は未検証で、#628とEpic #624は完了していない。

## 初回出力と方法

[固定条件](protocol.md)を先に用意し、条件ごとにfresh contextのCodex subagentを一つずつ使用した。
親のモデル設定を継承し、モデルの上書きはしていない。正確なbackend版・sampling設定・seedは
いずれの生成者にも観測できず不明。入力・prompt・Profile pins・原稿と実行結果を
`comparison-manifest.json`と関連の記録に保持する。

一条件一ケース一稿の計四稿で、保存後の改善再生成はない。
文字数はsection contentのUnicode文字数で、見出し・改行を含む。

| ケース | baseline（Writer 1.1.0・旧配信） | current（Writer 1.4.0・修正後配信） |
| --- | --- | --- |
| 具体的変更・効果未測定 | 3,209字 | 2,703字 |
| 反対結果による正当な保留 | 3,110字 | 2,741字 |

目標は各稿3,000〜4,500字。現行側は二稿とも未達であり、そのずれを保持した。
短いことを読者効果の改善とは数えない。

親は全四稿を読んだ。別のfresh contextモデルにも、条件・Profile・生成記録を見せず、
固定研究材料とM/Nラベルの本文だけで点検を依頼した。ラベル対応はケース間で交差させた。
これはモデルによる条件名を伏せた点検であり、人間の独立レビューや統計的な盲検試験ではない。
その初回所見も変更せず保存する。親の所見とモデル所見を同一の独立評価とは扱わない。

## 主張・理由・条件の比較

### 具体的変更と未測定の効果

baselineの中心文は「通常案件については、受付済みの共通アカウント項目をトリアージへ
再利用し、同じ項目の二重入力をやめることを提案する」。currentは「通常案件では
共通アカウント項目を再利用し、二重入力をやめる」。語尾は異なるが、どちらも同じ変更を答え、
新たな会議・調査・PoCの検討だけに置き換えていない。

両稿とも、300件中96件の重複と、その96件の再入力時間中央値2分を根拠に置く。
理由は同一項目の再入力をその項目の再利用に置き換える対応関係であり、
処理時間短縮・誤入力減少が実証されたという説明にはしていない。
例外案件の入力と本人確認を維持し、効果は未測定、提言採択と施策実施は別と記している。

### 反対方向の結果と正当な保留

baselineは「全案件への一律展開を保留することである」、currentは「全案件への一律展開は
保留する」と答える。どちらも通常8→6分/件と例外4→5分/件を結果本文で並べる。
因果・差の原因は分離されていないため、例外案件の案件構成と同時期の変更を調べ、
案件構成を記録した比較の後に適用範囲を判断するという理由と次の作業を保持する。
正当な保留を強い導入判断へ変えていない。

| 失敗の次元 | 親による四稿の点検 |
| --- | --- |
| 実証を超える効果・因果の主張 | 中心の結果・提言では観察されない。 |
| 入力にない規範判断 | 新たな会議、PoC、確認廃止、期限・担当の追加は観察されない。一方、blind点検は基準稿の「同じ重さで読む」に懸念を示した。 |
| 反対結果の脱落 | 両条件で例外案件の上昇を本文に保持。 |
| 中心の結論の消失・弱化 | 両条件で具体的変更を保持。単なる検討課題への変換なし。 |
| 正当な保留の破壊 | 両条件で保留と次の比較を保持。 |

この表は総合点やsemantic PASSではなく、固定材料に対する限定所見である。
blind点検の懸念は、保留ケースのbaseline導入部にある「同じ材料にある例外案件の上昇も
同じ重さで読む」である。両結果を保持することと、判断上の重みを等しく決めることは同義ではない。
中心判断の破壊とは断定しないが、入力にない重みづけの可能性を懸念として保持する。
これを五種類の失敗の疑いとして保守的に扱い、このケースだけ追加対照Cの対象にした。
疑いを除外して都合よく追加対照なしと結論しない。

## 残る編集上の問題

両条件で、数値・未測定・採択と実施の区別を複数節で繰り返している。
たとえばbaselineの変更ケースは、導入部の最終段落で採択と実施の説明を再度挟み、
結果の最終段落で中央値の限定を重ね、結論の最終段落で同じ区別を繰り返す。
必要な条件を一度示すことは問題ではないが、この反復は本文を進める追加情報が少ない。
currentにも、節末で同じ限定を重ねる箇所がある。規則の有無だけで解消したとは言えない。

currentの保留ケース・結果第2段落の「提示された値を合わせて全体平均を計算する根拠はなく」
という表現も、限定の書き方として注意が要る。各区分・各期間20件という入力から標本内の
集計値を計算することと、全案件への効果を結論することは別である。入力が全体効果を
示していないことを、計算自体の不可能性に広げない。原稿は改変せず、具体的な編集課題として残す。

次の編集では、共通の方法・集計上の注意を方法・結果へまとめ、変更の結論には判断を変える
条件と未測定の効果を簡潔に残す。既存Writing Feedbackとexact-base改稿で扱える。
新たな研究採択や保存時の文章品質gateは必要ない。

## 追加対照・構造確認・限界

追加対照Cは、Writer 1.4.0のまま正のbrief配信だけを除き、保留ケースを一稿だけ生成する。
一条件一ケース一回の上限を守り、有利な出力を得るための改善再生成は行わない。
この追加生成は単独ケースのfresh contextであり、先行ケースの生成履歴がある
当初の条件とはホスト文脈が完全には揃わない。この点も個別効果の識別を制限する。
両条件に同趣旨のWriter入口と
研究側の明示的な答えがあり、版と正のbrief配信も同時に異なるため、個別変更の効果は
独立に識別できない。四稿だけから一般的な文章改善や害の不存在を推定しない。

当初の四稿は既存wrap-responseで本文bytesを変えず応答に包み、公開importがIMPORTED、
同じ応答の再送がVERIFIED_REUSEとなり、inspectで保存稿を確認した。
未実施のProfile点検はunevaluatedのままで、文書全体の点検・公開承認は申告していない。
全入力はSYNTHETIC_TEST_ONLY、preview_only=true、release_eligible=falseを保つ。

これは配信・履歴・保全と限定的な本文比較の確認である。
Work実機・実原稿・実読者の評価は[引渡し資料](work-handoff.md)に残す。
