# Qualitative, Case, Cross-case, and Model Writing

## Case rendering

Before a case, state its approved selection reason and role when supplied. Then write facts, statements, and observations before any approved assessment/meaning. Honor permission, anonymization, company-name disclosure, and manuscript-confirmation status.

Never turn an interview statement into a general fact. Never present a small set of cases as representative unless the Research State explicitly contains an approved scope/generalization judgment.

## Cross-case synthesis

Only synthesize across cases when the Research State supplies approved comparison axes and approved comparison results. Arrange cases so the approved axis is comparable; then state supplied commonalities, differences, exceptions, unknowns, and approved applicability range. Do not discover the axis or synthesis yourself.

## Case → model refinement

This is a reader-facing transformation of an **already approved** research revision. Use it only when all research decisions needed for the revision are supplied.

Render, in a coherent order:

1. what happened in each relevant case (facts/observations);
2. supplied cross-case commonalities/differences/exceptions;
3. which old proposition/model assumption the approved analysis says was insufficient;
4. what the approved decision retained;
5. what it changed, removed, or added;
6. the approved revised model/proposition;
7. supplied remaining uncertainty, boundary condition, minority warning, or judgment-impossible point.

Status labels such as `SUPPORT`, `CONDITION_ADDED`, `PARTIALLY_REFUTED`, `REFUTED`, or `JUDGMENT_IMPOSSIBLE` may exist internally. In body prose, render their approved meaning naturally rather than printing the status code.

If the Research State contains an observed mismatch but does not contain the approved revision or reason, do not repair the model. Output the observable mismatch if useful, then `[NEEDS_INPUT: approved model revision and revision reason]`. Return the same issue separately as Publication Feedback with `type: MODEL_REVISION_UNRESOLVED`, normally routed to `RESEARCH`, and mark it blocking when the requested model-revision prose cannot be completed.

## Model introduction

Write a model/framework only if its introduction and structure are approved. Explain formation reason, purpose/position, components, relations, scope, and implementation elements only where present. Do not invent stages, maturity levels, KPIs, actors, procedures, or expected effects.
